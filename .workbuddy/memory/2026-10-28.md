## LOD 崩溃修复（21:12 崩溃报告 + 高度全 -64）
两个致命错误，均已修复并 EXIT=0：

### 错误一：Missing elements in vertex: Normal（崩溃）
- 根因：BLOCK 顶点格式实际是 32 字节 = Position(12)+Color(4)+UV0(8)+UV2(4)+Normal(3)+padding(1)。我之前误判为 28 字节且移除了 setNormal。
- 修复：LODMesh.VERTEX_STRIDE 28→32，putVertex 增加 nx,ny,nz 三个有符号 byte（×127）+ 1 padding；GreedyMesher 三个 emit 补法线（顶面 0,1,0；X侧面 ±1,0,0；Z侧面 0,0,±1）；writeMesh 读法线并 setNormal(float,float,float)。
- 用 javap 反编译 DefaultVertexFormat 确认 BLOCK 元素顺序与 32 字节步长。

### 错误二：高度图全 -64（真正根因，非位运算错误）
- 根因：Minecraft 1.21.1 高度图类型随区块 Status 变化——只有 `minecraft:full` 区块才持久化 MOTION_BLOCKING/WORLD_SURFACE 等；`structure_starts`/`biomes`/`carvers`/`initialize_light` 早期区块只有 WORLD_SURFACE_WG/OCEAN_FLOOR_WG。McaRegionReader 只读 MOTION_BLOCKING，读不到 → null → 全填 minBuildY=-64。
- 用 Python 直接解析存档 .mca 实证：region r.-2.-1.mca 219 区块中 194 个 structure_starts、仅 2 个 full；full 区块 MOTION_BLOCKING 解码 Y=[72,77] 完全正确（9-bit 位运算本身没错，37 个 long 存储 256 条目）。
- 修复：extractMotionBlockingHeightMap 改为按 fallback 顺序取第一个存在的 long[]：MOTION_BLOCKING → MOTION_BLOCKING_NO_LEAVES → WORLD_SURFACE → WORLD_SURFACE_WG → OCEAN_FLOOR → OCEAN_FLOOR_WG。
- 关键知识点（永久记录）：9-bit 高度图位打包 = mask(1<<9)-1，valuesPerLong=64/9=7，longIndex=idx/7，offset=(idx%7)*9，绝对Y=minBuildY+值；存储 256 条目需 37 个 long。

## LOD "看不到" 根因定位与修复（21:34，帧数已正常但看不到 LOD）
诊断日志：高度 Y=[64,68] 正确、首 mesh 世界原点 (-560,48)、相机 (-463,70,288)、可见 mesh 数=7、顶点数=1292 —— 数据/坐标/剔除全对，但画面不显示。

### 根因（决定性）
Ribbon 本身是 **Embeddium fork**（日志 258 行 "Ribbon (Embeddium fork) 1.0.15 (embeddium)"），且用户开着 **Iris 光影**（iterationT/Sundial/derivative）。

用 javap 反编译确认关键机制：
1. Embeddium 用 @Overwrite 重写了 LevelRenderer.renderSectionLayer，走 `dispatchRenderStage(RenderType, ..., Matrix4f pose, Matrix4f matrix, ...)` 这个**无 PoseStack 的重载** → RenderLevelStageEvent.getPoseStack() 返回的是**空单位 PoseStack**（构造器里 ifnull→new PoseStack()），`pose.last().pose()` = 单位矩阵，不含相机旋转。
2. 旧代码 `addVertex(pose.last(), x-camX,...)` 用单位矩阵变换 → 顶点只有"世界-cam"平移、**缺相机旋转** → 几何方向错乱/偏出屏幕 → 看不到。
3. Embeddium 的 DefaultChunkRenderer 显式 `shader.setModelViewMatrix(matrices.modelView())`，不走 RenderSystem.modelView 栈；`RenderType.solid()` 的 BufferBuilder flush 时 RenderSystem.modelView 是单位矩阵，不会自动应用旋转。
4. GameRenderer 确认 `modelView = new Matrix4f().rotation(camera.rotation().conjugate())` —— 纯旋转 view 矩阵，不含平移。

### 修复
LODRenderEventHandler：改用 `event.getModelViewMatrix()`（纯旋转 view 矩阵，原版/Embeddium 都非空）+ 顶点减相机位置，即 `addVertex(modelView, x-camX, y-camY, z-camZ)` = view旋转*(世界-cam) = 相机空间坐标。彻底替代旧 `addVertex(pose.last(), ...)`。

### 关键知识点（永久记录）
- NeoForge RenderLevelStageEvent 在 Embeddium 下 getPoseStack() 返回空单位矩阵（不是 null，构造器有 ifnull 兜底），不能依赖它做相机旋转。
- 正确做法：`event.getModelViewMatrix()` 是纯旋转 view 矩阵，用它 `addVertex(modelView, worldX-camX, ...)` 得到相机空间坐标。
- 验证：javac --release 21 -proc:none 编译 EXIT=0。

## LOD 事件"永远不触发"根因（22:18，用户反馈搜不到[心跳]日志）

用户报告最新 jar 里搜不到 [心跳] 日志 → `onRenderLevel` 根本没被触发。暴力排查 + javap 字节码级定位，发现**决定性根因**：

### 根因（决定性，此前所有"看不到"修复都建立在错误的 Stage 前提上）
`RenderLevelStageEvent.Stage` 枚举的 static 初始化块（javap 反编译）：
```
AFTER_SKY              → register("after_sky", null)
AFTER_SOLID_BLOCKS     → register("after_solid_blocks", RenderType.solid())
AFTER_CUTOUT_*         → register(..., RenderType.cutoutMipped()/cutout())
AFTER_ENTITIES         → register("after_entities", null)   ← RenderType 是 null！
AFTER_BLOCK_ENTITIES   → register("after_block_entities", null)
AFTER_TRANSLUCENT_BLOCKS → register(..., RenderType.translucent())
```
而 Embeddium（Ribbon 是 Embeddium fork）用 @Overwrite 重写 renderSectionLayer，走
`ClientHooks.dispatchRenderStage(RenderType, ...)` 这个**无 PoseStack 的重载**。该重载字节码：
```
Stage stage = Stage.fromRenderType(renderType);  // 查 RENDER_TYPE_STAGES map
if (stage == null) return;                        // 查不到直接 return
```
`fromRenderType` 只对 map 里注册了具体 RenderType 的 Stage 返回非 null。
`AFTER_ENTITIES` 注册的是 null → `fromRenderType(solid())` 永远查不到 AFTER_ENTITIES
→ **AFTER_ENTITIES 事件在 Embeddium 下永远不会 post** → onRenderLevel 永远不触发。

### 修复
`LODRenderEventHandler.onRenderLevel` 的 Stage 判定从 `AFTER_ENTITIES` 改为
`AFTER_SOLID_BLOCKS`（映射 RenderType.solid()，Embeddium 一定触发）。语义等价：
solid 几何已入深度缓冲，LOD 用 RenderType.solid() 提交仍能正确深度测试。
同时在方法第一行（所有 if 之前）加 `System.out.println("[LOD] Render Event Fired! Stage="...)` 生死日志。

### 关键知识点（永久记录）
- NeoForge RenderLevelStageEvent 的 Stage 分两类：映射到具体 RenderType 的
  （AFTER_SOLID_BLOCKS/CUTOUT/TRANSLUCENT）能在 Embeddium 的 RenderType 重载下触发；
  映射到 null 的（AFTER_ENTITIES/AFTER_BLOCK_ENTITIES/AFTER_SKY 等）在 Embeddium 下【永不触发】。
- 监听 LOD 必须用 AFTER_SOLID_BLOCKS，不能用 AFTER_ENTITIES。
- 事件总线确认：RenderLevelStageEvent 在 NeoForge.EVENT_BUS（GAME 总线）post，
  @EventBusSubscriber(modid=..., value=Dist.CLIENT) 默认 bus=GAME 正确，无需 bus=Bus.MOD。
- @EventBusSubscriber 无需手动 register，注解自动注册；Ribbon.java 主类无手动 register 是正常的。
- 红线：未触碰 build.gradle/gradle.properties/neoforge.mods.toml。

## LOD 真空带根因（22:31，用户反馈"只能看到原版区块"）

移除 Iris 短路后重新编译，日志证实**渲染链路全部健康**：
- 事件触发、调度器 running、ready mesh 78→91 稳定产出、每帧提交可见 mesh（顶点数 360）。
- 矩阵验证决定性结果：`modelView` 有非对角元素（相机 yaw 旋转，m00/m01 随帧变化），
  `pose` 恒为单位阵（1.0,0.0,0.0）→ **坐实 modelView bake 旋转方向正确**。
- m10 恒 0 → 玩家平视无 pitch，符合场景。

但画面仍看不到 LOD。读 options.txt 找到**真正根因**：
```
renderDistance:2   ← 原版渲染距离只有 2 区块（32 格）！
simulationDistance:12
```
旧请求逻辑写死"跳过 |dx|,|dz|<=4 的近处"→ LOD 环带是 5~8 区块（80~128 格），
而原版只渲染 2 区块（32 格）→ **32~80 格之间是真空带**（原版不渲染、LOD 不覆盖），
LOD 画在 80 格外太远，被真空带割裂，肉眼看不到。

### 修复
1. Config：LOD_RADIUS_CHUNKS 上限 32 → 1024（用户要求）。
2. MixinLODLifecycle 请求逻辑重写：
   - 内圈从写死 4 改为 `max(options.getEffectiveRenderDistance(), 2)`，
     从原版有效渲染距离之外开始接管，消除真空带。
   - 环带遍历改为"环形边界遍历"（每层环只遍历四条边，约 8*ring 个区块），
     避免 O(radius²) 爆炸；requestLOD 内部 MAX_IN_FLIGHT/MAX_READY_MESHES 兜底。

### 关键知识点
- `Options.getEffectiveRenderDistance()` 返回实际生效的渲染距离（区块），比
  `renderDistance().get()` 更准确（考虑 serverRenderDistance）。
- LOD 内圈必须紧跟原版有效渲染距离，写死常量会在 renderDistance 小（2~4）时
  制造真空带，在 renderDistance 大（16~32）时与原版重叠。

## 决定性根因：LOD 网格顶点绕序反了 → 背面剔除，一个像素都画不出

**现象**：日志显示渲染链路全健康（事件触发、调度器 running、ready=78~92、
矩阵变换正确 modelView 有旋转而 pose 单位阵、可见 mesh 数=16、每帧提交），
但画面完全看不到 LOD。

**根因（字节码级实证）**：GreedyMesher 的三个 emit quad 的顶点绕序全是
**顺时针（CW）**，而 Minecraft 正面约定是**逆时针（CCW）**，且
`RenderType.solid()` 默认启用背面剔除（CULL）。→ 16 个 mesh 全部被 GPU 剔除。

**权威证据**：javap 反编译 NeoForge `FaceInfo.class` 的 `<clinit>`，原版各面
CCW 顶点顺序（MIN/MAX 指 16×16 方块边界）：
- UP(+Y)：西北(MIN_X,MIN_Z) → 西南(MIN_X,MAX_Z) → 东南(MAX_X,MAX_Z) → 东北(MAX_X,MIN_Z)
- EAST(+X)：上北(MAX_Y,MAX_Z) → 下北(MIN_Y,MAX_Z) → 下南(MIN_Y,MIN_Z) → 上南(MAX_Y,MIN_Z)
- SOUTH(+Z)：上西(MIN_X,MAX_Y) → 下西(MIN_X,MIN_Y) → 下东(MAX_X,MIN_Y) → 上东(MAX_X,MAX_Y)

`RenderStateShard$CullStateShard(true)` → `RenderSystem.enableCull()`，solid 默认 cull。

**修复**：GreedyMesher.java 三个 emit 方法（emitTopQuad/emitSideQuadX/emitSideQuadZ）
的 putVertex 顺序全部改为原版 CCW。侧面双面发射的两组绕序都修正。

**关键知识点（永久记录）**：
- Minecraft 正面 = 逆时针 CCW（OpenGL 默认 frontFace，从未被改）。
- RenderType.solid() 启用背面剔除，绕序反了会"提交了顶点但一个像素都看不到"，
  这是最隐蔽的"不可见"根因——比坐标、矩阵、光照都难排查。
- 验证绕序的最权威方式：javap 反编译 `FaceInfo.class` 的 static 初始化块，
  直接读原版每个 Direction 的 4 个 VertexInfo 坐标顺序。
- 编译验证 classpath 陷阱：find 的 jar 路径前缀必须是完整 Maven 坐标
  （org.slf4j/...），Windows 下 javac 的 classpath 用分号 `;` 分隔且 build 目录
  用反斜杠 `\` 才能被正确识别（正斜杠 + 冒号在部分场景下失败）。

## 决定性根因：SPSC 队列被 18 个后台线程并发 enqueue → 竞态损坏 mesh 引用

**现象**：三重诊断全部打印后，顶点追踪日志暴露铁证：
`[顶点追踪] 世界=(2.75E-43, 4.601E-41, 7.471E-41)` —— 顶点世界坐标是接近 0 的
垃圾浮点（本应 -512, 416, 67 这类值），说明渲染线程读到的 DirectByteBuffer 是
被 recycle() 清零的、或从未正确写入的 buffer。

**根因（决定性）**：`LODManager.readyQueue` 用的是 `LockFreeQueue`（SPSC 单生产者
无锁队列），但 `requestLOD` 里 `ex.execute(() -> {... readyQueue.enqueue(mesh) ...})`
是在 18 个 worker 线程的线程池里并发调用的——**违反 SPSC「单一生产者」契约**，
多线程并发 enqueue 竞态损坏 producerIndex 游标/槽位，mesh 引用错乱、丢失、或指向
已 recycle 的清零 buffer。这正是「LOD 不稳定、时有时无、看不到」的总根源。

**修复（LODManager.java 单文件）**：
- `LockFreeQueue<LODMesh>` → `ConcurrentLinkedQueue<LODMesh>`（多生产者安全 MPSC）
- `enqueue/dequeue/drain` → `offer/poll` + 手动 while 循环（限 64/批）
- 去掉「队列满丢弃」分支（无界队列，由 MAX_READY_MESHES=256 消费侧兜底）

**关键知识点（永久记录）**：
- LockFreeQueue 是「严格 SPSC」，enqueue 只能单线程调用；线程池多 worker 并发
  生产必须用 ConcurrentLinkedQueue 或 MPMC 队列，否则游标竞态 → 数据损坏。
- 顶点坐标变成 2.75E-43（≈0x00000003）是「读到了清零/未写 DirectByteBuffer」的
  标志性特征，直接指向 mesh 生命周期/队列竞态，而非坐标变换或矩阵问题。
- 之前的「矩阵 modelView 有旋转而 pose 单位阵」结论仍然正确（绕序、矩阵、管线
  都健康），真正卡住「看不见」的是这个队列竞态。

## 最终根因：ByteBuffer 字节序用 nativeOrder() 导致顶点坐标字节序反转

**现象**：SPSC 队列修复后，顶点追踪日志仍读垃圾：
`[顶点追踪] 世界=(7.202E-41, 4.601E-41, 5.4621E-41)`。

**决定性证据（Python 字节级分析）**：
- 正确世界坐标：(-400.0, 64.0, 304.0)，小端字节 = `00 00 c8 c3` / `00 00 80 42` / `00 00 98 43`
- 日志读到的垃圾值按小端字节 = `c3 c8 00 00` / `42 80 00 00` / `43 98 00 00`
- 而这正是 -400.0/64.0/304.0 的**大端**表示！`00 00 c8 c3` 按大端 getFloat = 7.2019e-41。
- 铁证：数据以小端正确写入，但 getFloat 按大端读出 → **字节序反转**。

**根因**：`LODMesh.acquire`/`ensureCapacity` 用 `ByteOrder.nativeOrder()` 设 buffer 字节序。
Minecraft/LWJGL 顶点数据一律小端，但 nativeOrder() 在此运行环境（或 JVM 配置）返回
了非预期结果，导致 putFloat 与 getFloat 字节序不一致。

**修复（LODMesh.java）**：
- `ByteOrder.nativeOrder()` → `ByteOrder.LITTLE_ENDIAN`（显式小端，acquire + ensureCapacity 两处）
- 顺带修复 ensureCapacity 单位 bug：`(vertexCount+additionalBytes)*VERTEX_STRIDE` →
  `vertexCount*VERTEX_STRIDE+additionalBytes`（原式把字节数当顶点数，严重过度分配）

**关键知识点（永久记录）**：
- Minecraft/LWJGL 顶点 buffer 一律显式小端，**绝不能用 nativeOrder()**。
- 顶点坐标变成 7.2E-41 这类"接近 0 但非 0"的浮点，是**字节序反转**的指纹特征：
  大端读小端写（或反之）会把正常浮点读成 denormal 极小值。
- 诊断手法：把读到的垃圾 float 的字节 dump 出来（hex），与正确值的两种字节序
  （struct.pack '<f' 和 '>f'）比对，一眼定位字节序问题。
- 之前的 SPSC 队列竞态修复仍有效（多生产者必须 ConcurrentLinkedQueue），但
  字节序才是"顶点数据垃圾"的直接根因。
