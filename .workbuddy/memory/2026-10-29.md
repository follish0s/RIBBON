## 决定性根因：Iris 的 FullyBufferedMultiBufferSource 清空了 endBatch(RenderType)，LOD 顶点从不 flush

**现象**：顶点数据正确（Python 证实小端读出坐标完美：-576/63/480、-48/72/-64）、
modelView 矩阵正确、相机相对坐标正确、事件在 AFTER_SOLID_BLOCKS 触发、提交了 21 个
mesh，但屏幕上 LOD 仍然不可见。用户判断"是 Iris 没干活 / Embeddium 没让 LOD 加载"。

**决定性证据（反编译 Iris 1.8.12 字节码）**：
1. `MixinRenderBuffers.batchedentityrendering$replaceBufferSource`：光影开启期间
   （begins>0），`mc.renderBuffers().bufferSource()` 返回
   `FullyBufferedMultiBufferSource`（完全缓冲 + 排序的 MultiBufferSource）。
2. `FullyBufferedMultiBufferSource.endBatch(RenderType)` 的字节码只有一条 `return` ——
   **空实现，不 flush**。我们代码里的 `buffers.endBatch(RenderType.solid())` 在光影下
   变成空操作，顶点写进 buffer 但永不 flush 成 draw call。
3. `FullyBufferedMultiBufferSource.endBatchWithType(TransparencyType)` 才是真正的 flush
   入口：内部 readyUp() + 遍历 renderOrder 里匹配该类型的 RenderType，逐个
   setupRenderState() + 绘制。
4. `batchedentityrendering$beginTranslucents` 字节码铁证：Iris 自己在实体渲染后、
   半透明前，正是用 `endBatchWithType(TransparencyType.OPAQUE)` +
   `endBatchWithType(TransparencyType.OPAQUE_DECAL)` 来 flush 不透明实体。
5. `MixinCompositeRenderType.batchedentityrendering$onCompositeInit`：用
   TransparencyStateShard 分类，`RenderType.solid()` 是 NO_TRANSPARENCY → 归为
   `TransparencyType.OPAQUE`。
6. `MixinRenderType.redirectSetupRenderState`：`ImmediateState.mergeRendering` 控制
   setupRenderState 是否被跳过（merge 时跳过），flush 时正常调用 setupRenderState
   绑定 shader。

**修复（2 文件）**：
- `IrisReflection.java` 新增 `flushOpaqueViaIris(Object buffers)`：反射检测 bufferSource
  是否为 `FullyBufferedMultiBufferSource`，是则反射调用
  `endBatchWithType(TransparencyType.OPAQUE)`（枚举常量用 getEnumConstants() 遍历，
  不能用 java.util.Enum.valueOf —— --release 21 下泛型签名报错）。
- `LODRenderEventHandler.java` 提交后改为：
  `if (!IrisReflection.flushOpaqueViaIris(buffers)) buffers.endBatch(RenderType.solid());`
  （非 Iris 环境回退原版 endBatch）。

**验证**：javac --release 21 -proc:none 编译 EXIT=0，零错误零警告。

**关键知识点（永久记录）**：
- **Iris 光影开启时绝不能调用 `bufferSource().endBatch(RenderType)`** —— 它被 Iris
  重写成空操作。必须走 `endBatchWithType(TransparencyType)` 或反射 Iris 的
  FullyBufferedMultiBufferSource。
- Iris deferred 渲染下，mod 通过 BufferSource 提交的顶点走的是 **batched entity
  rendering 路径**（不是 terrain 的 SodiumPrograms），用 entity/fallback shader 渲染，
  光照可能不如 terrain gbuffer 完美，但几何能正确显示（先解决"可见"）。
- Iris 的 terrain chunk 渲染（SodiumPrograms）只给 Embeddium 的 TerrainRenderPass 用，
  BufferSource 即时提交进不去。
- 反编译运行版 neoforge-21.1.259-client.jar 在
  `美西螈/meta/libraries/net/neoforged/neoforge/21.1.259/`；MultiBufferSource 等
  Mojang 混淆类不在 neoforge jar 里（在 client.jar 本体），反编译 MC 类要用
  `.gradle/caches/minecraft/versions/1.21.1/client.jar`。
- 编译 classpath 完整清单（下次直接用，路径用 C:/ 或 D:/ 前缀，分号分隔）：
  neoforge-21.1.61.jar + nf_stubs_cls + build/classes/java/main + bus-8.0.5 + mixin-0.8.5
  + slf4j-api-1.7.36 + guava-31.1-jre + joml-1.10.8 + fastutil-8.5.12 + annotations-24.0.1

## 第二轮：flush 修复后仍不可见 → 改用「自定义 Shader + 独立 VBO」隔离渲染（Voxy 式安全变体）

**进展**：`endBatchWithType(OPAQUE)` 修复编译进 jar（已确认 flushOpaqueViaIris 存在于
mods 里的 jar），但用户仍反馈看不见。日志确认顶点/坐标/矩阵全对，问题纯在 Iris
deferred 管线对原版 RenderType 的层层拦截（顶点格式被 monocle/Iris 的 vertexformat
mixin 转换、shader 被替换、phase 错位）。

**用户拍板的方向（关键）**：采纳"Voxy 思路的安全变体"——自定义 RenderType + 独立

glBindBuffer/glDrawArrays（Iris deferred 下会崩），所有 GL 调用必须封装在 MC 管线的
受控上下文（VertexBuffer/ShaderInstance）。

**本轮实施（5 个文件 + 3 个 shader 资源）**：
1. `assets/ribbon/shaders/core/lod_terrain.{json,vsh,fsh}`：独立 shader，不继承
   rendertype_solid 等原版模板（Iris 只替换它认识的内置 shader），POSITION_COLOR

2. `LODShaderRegistry.java`（新）：RegisterShadersEvent 注册 ShaderInstance，volatile

3. `LODVboUploader.java`（新）：把 LODMesh 32 字节 BLOCK 顶点重打包成 16 字节
   POSITION_COLOR，Tesselator.begin(QUADS, POSITION_COLOR) → buildOrThrow() → MeshData
   → VertexBuffer.upload()。只在渲染线程调用。
4. `LODMesh.java`：加 gpuBuffer/gpuVersion 字段 + gpuUploaded()/setGpuBuffer()，
   recycle() 时 close GPU buffer。
5. `LODRenderEventHandler.java`：渲染阶段 AFTER_SOLID_BLOCKS → AFTER_TRANSLUCENT_BLOCKS；
   放弃 bufferSource()+RenderType.solid()，改为 shader + VertexBuffer.bind() +
   drawWithShader(fullView, proj, shader) + unbind()。删除 writeMesh。

**关键 API 确认（反编译 1.21.1 srg jar + NeoForge 21.1.259 运行版）**：
- `VertexBuffer.upload(MeshData)`（1.21.1 新签名，不是旧 RenderedBuffer）；

  setDefaultUniforms + apply + draw + clear（无需手动 apply）。

- `ShaderInstance(ResourceProvider, ResourceLocation, VertexFormat)`；`apply()`/`clear()`。

- `RegisterShadersEvent.registerShader(ShaderInstance, Consumer<ShaderInstance>)`。

  右乘 = R·T(-cam)），event.getModelViewMatrix() 是纯旋转 R。

## 第四轮：真正的根因 = Iris 拦截未知 shader（禁用颜色写入）→ allowUnknownShaders 修复

**现象**：shader 注册成功后仍看不见。日志确认 shader 注册成功、顶点/矩阵正确、渲染循环执行，
但无 VBO 上传失败日志，屏幕上仍无 LOD。

**根因（字节码级铁证，反编译 Iris 1.8.12）**：
1. Iris 光影开启时 `IrisRenderingPipeline.isRenderingWorld=true`。
2. `shouldOverrideShaders() = isRenderingWorld && isMainBound`（world render 期间恒 true）。
3. `MixinShaderInstance.iris$shouldSkipThis()`：当 `allowUnknownShaders=false`（IrisConfig 默认
   iconst_0）时，对非 ExtendedShader/FallbackShader 的普通 ShaderInstance 返回
   `shouldOverrideShaders()` = **true**。
4. `onTail`（apply 后回调）：`shouldSkipThis()==true` → 调 `DepthColorStorage.disableDepthColor()`
   **禁用颜色写入** → LOD 画了但颜色被丢弃，完全不可见。

**之前所有判断的修正**："自定义 shader 不会被 Iris 拦截"是**错的**——Iris 拦截所有未知 shader，
只是不替换 shader、而是禁用颜色写入 + 重绑 framebuffer。

**修复**：
- `IrisReflection.allowUnknownShaders()`（新）：反射拿 `IrisConfig.allowUnknownShaders` 字段
  直接 `Field.setBoolean(true)`，**不调 setUnknown()**（后者会 save() 写盘，有副作用）。
- `LODRenderEventHandler` 在拿 shader 后调 `allowUnknownShaders()`。
- 效果：`shouldSkipThis()` 走 allowUnknownShaders=true 分支，对 shouldSkip==NONE 的 shader 返回
  false，不再 disableDepthColor()。onTail 会调 bindDefault()（绑主 framebuffer），反而帮助 LOD 画到屏幕。

**附带**：本轮还加了「提交诊断」日志（可见/实际draw/上传失败数），并把视锥剔除临时改为距离粗筛
（64 区块内），用于二分"视锥误杀 vs 渲染管线"两类根因（现已确认是渲染管线，可后续恢复视锥剔除）。

**关键 API 记录**：
- `IrisConfig` 字段：allowUnknownShaders(boolean, 默认 false)、shadersToSkip(List<ResourceLocation>)、
  enableShaders。方法 setUnknown(boolean) 会 save() 写盘。
- `IrisRenderingPipeline` 字段：isRenderingWorld、isMainBound、isBeforeTranslucent、defaultFB、
  defaultFBAlt、defaultFBShadow。shouldOverrideShaders()=isRenderingWorld&&isMainBound。
- `MixinShaderInstance`：shouldSkip 字段(MethodHandle)，SkipList.NONE/NONE_FORCE/ALWAYS；
  isKnownShader()=instanceof ExtendedShader||FallbackShader。

**验证**：javac --release 21 编译 5 文件 EXIT=0（仅无害 deprecation）。

**待用户**：完整构建 + 进游戏测试。期望日志出现「已置 Iris allowUnknownShaders=true」和「提交诊断
实际draw>0」，LOD 应该能显示（纯色 + 雾）。

## 第五轮：距离粗筛阈值 bug（4096=64 方块而非 64 区块）→ visible 恒空，LOD 永不绘制

**现象（20:57 日志）**：shader 注册成功、调度器 ready=94 稳定、矩阵验证正常输出，但
「视锥诊断」「顶点追踪」「提交诊断」「已置 allowUnknownShaders」等一次性日志**全都没出现**。
证明代码卡在 `if (visible.isEmpty()) return;`。

**决定性根因**：第四轮把视锥剔除临时改成「距离粗筛」，代码 `dx*dx + dz*dz <= 4096.0`。
注释写"64 区块 = 1024 方块"是**错的**——4096 开方是 **64 方块（仅 4 区块）**，不是 64 区块。
而 LOD 环带位于原版 renderDistance（≥8 区块=128 方块）之外，64 方块的粗筛把玩家外围所有
LOD 全部过滤 → `visible` 恒为空 → LOD 永不绘制。

**附带确认的两个隐藏 bug**：
1. `MixinLODLifecycle` 环带遍历 `for(ring=innerRadius; ring<=radius)`：当 renderDistance
   (innerRadius) > LOD 半径 (radius=8) 时循环体一次不执行 → 请求不到新区块。
2. `evictFarAway` 淘汰半径 = radius+2（10 区块），但请求环带外半径 = innerRadius+radius
   （可达 16~20 区块）→ 远端 mesh 刚生成就被淘汰，形成「请求→生成→淘汰→再请求」死循环。

**相机矩阵已确认正确（字节码级）**：反编译 joml `Matrix4f.translate` 的 `translateGeneric`
字节码：`m30' = m00*x + m10*y + m20*z + m30`，即**右乘** `this = this * T(x,y,z)`。所以
`fullView = new Matrix4f(modelView).translate(-camX,-camY,-camZ)` = `modelView * T(-cam)`
= `R·T(-cam)`，这是**正确的 view 矩阵**（先平移 v-cam，再旋转 R）。`event.getModelViewMatrix()`
实测是纯旋转（m03=m13=m23=0），补平移方向正确。`VertexBuffer.drawWithShader` 字节码确认：
内部 `setDefaultUniforms(mode, mv, proj, window)` 直接把传入矩阵设为 ModelViewMat/ProjMat
uniform → apply → draw → clear，无需手动 apply。**相机不是本轮根因，矩阵逻辑本来就对。**

**本轮修复（2 文件）**：
1. `MixinLODLifecycle.java`：环带遍历改 `for(ring=innerRadius; ring <= innerRadius+radius)`。
2. `LODRenderEventHandler.java`：
   - 移除错误的 64 方块距离粗筛，改用 `LODFrustumCuller.cull(ready, frustum)`（原版 Frustum
     AABB 视锥剔除，O(n) 正确）。
   - 远距上限改 `radius*16` 方块（非硬编码 64）。
   - `evictFarAway` 淘汰半径改 `innerRadius + radius + 2`（与请求环带一致）。

**编译验证**：`./gradlew compileJava`（需 `export JAVA_HOME=美西螈/meta/java_versions/oracle-jdk-21`）
BUILD SUCCESSFUL，2 executed。

**关键教训（永久）**：日志里 ready=94 但 visible 为空时，先查"距离/视锥粗筛的阈值单位"，
别再怀疑渲染管线。本轮距离粗筛的 4096 是"64 方块"不是"64 区块"，注释与代码不一致是元凶。

## 第六轮：draw=15 但不可见 → 真根因 = Iris onTail 把 framebuffer 切到 bindDefault()

**现象（21:19 日志）**：距离粗筛修复后，所有诊断日志齐了：视锥诊断（候选37/可见15）、
顶点追踪（世界-208,70,192 → view -20,62,-236 正确）、提交诊断（可见15/实际draw15/上传失败0/
shader=lod_terrain）。**渲染循环真正 draw 了 15 个 mesh，但屏幕上仍然不可见。**

**决定性根因（字节码级，反编译 Iris 1.8.12 MixinShaderInstance + IrisRenderingPipeline）**：
1. `beginTranslucents()` 里 `deferredRenderer.renderAll()` 已把 gbuffer 合成到主 framebuffer，
   `copyPreTranslucentDepth()` 保证深度可用 → 所以 AFTER_TRANSLUCENT_BLOCKS 时 framebuffer
   **就是主 framebuffer**（之前"画进 Iris 管线 buffer"的推断是错的）。
2. 真正的坑在 `MixinShaderInstance.onTail()`（`ShaderInstance.apply()` 尾部回调）：
   ```
   if (shouldSkipThis()==false && isKnownShader()==false && shouldOverrideShaders()==true)
       → pipeline.bindDefault()   // 把 framebuffer 切到 Iris 默认 framebuffer！
   ```
   我的 lod_terrain 是普通 ShaderInstance：shouldSkipThis()=false（allowUnknownShaders=true 已生效）、
   isKnownShader()=false（非 ExtendedShader/FallbackShader）、shouldOverrideShaders()=true
   （=isRenderingWorld && isMainBound，world render 期间恒 true）。
   所以 `drawWithShader` 内部 `apply()` 触发 onTail → bindDefault() 切走 framebuffer → `draw()`
   画进 Iris 默认 framebuffer → `clear()` 触发 unlockDepthColorState → bindWrite(false) 切回。
   结果 LOD 画进了一个随后被 composite 覆盖的 buffer，主画面看不到。

**之前 summary 里"onTail 会 bindDefault() 反而帮助 LOD"的判断是错的**——bindDefault 绑的是
Iris 默认 framebuffer，不是主 framebuffer。

**修复**：
1. `IrisReflection.clearMainBound()/restoreMainBound()`（新）：反射拿 `PipelineManager.
   getPipelineNullable()` → `WorldRenderingPipeline.setIsMainBound(false/true)`。置 false 后
   `shouldOverrideShaders()=isRenderingWorld&&isMainBound=false`，onTail/unlockDepthColorState
   直接 return 不碰 framebuffer，LOD 画在当前（主）framebuffer。
2. `LODRenderEventHandler`：draw 前设置正确 RenderSystem 状态（enableDepthTest + depthMask(true)
   + depthFunc(519=GL_LEQUAL) + disableBlend + colorMask(true,true,true,true) + setShaderColor(1,1,1,1)
   + enableCull），draw 前 clearMainBound()，draw 后 restoreMainBound() + 恢复深度状态。
3. 新增 framebuffer 诊断日志：打印当前绑定 FB 与主 FB 的 ID 对比。

**关键 API 记录（Iris 1.8.12）**：
- `MixinShaderInstance.onTail/unlockDepthColorState/iris$shouldSkipThis/isKnownShader`；
  isKnownShader()=instanceof ExtendedShader||FallbackShader。
- `shouldOverrideShaders()=isRenderingWorld && isMainBound`（IrisRenderingPipeline 字段直读）。
- `WorldRenderingPipeline.setIsMainBound(boolean)`（公开接口方法）。
- `IrisRenderingPipeline.beginTranslucents()`：copyPreTranslucentDepth + deferredRenderer.renderAll()
  + enableBlend + setShader。
- `WorldRenderingPipeline.getDHCompat()` + `IrisRenderingPipeline.getDHTerrainShader()`：
  Iris 内置 Distant Horizons 兼容层（DHCompat.getDepthTex/getProjection/getNearPlane/getFarPlane），
  证明正确 LOD 渲染需走 Iris 深度纹理 + Iris 投影，而非原版 RenderLevelStageEvent 的矩阵。

**编译验证**：./gradlew compileJava BUILD SUCCESSFUL（2 executed）。

## 第七轮：渲染管线终于全通（framebuffer 一致 + draw=2），但游戏崩溃（scalablelux 线程冲突）

**现象（21:32 日志 + crash-report）**：
1. 上轮修复**全部生效**：`framebuffer诊断 当前绑定FB=2, 主FB=2, 一致=true, clearMainBound=true`、
   `提交诊断 可见=2, 实际draw=2, 上传失败=0`、`已置 allowUnknownShaders=true`、
   `Iris setIsMainBound 反射句柄就绪`。渲染循环真正 draw 了 2 个 mesh 到主 framebuffer。
2. 但随后**崩溃**：`IllegalStateException: Accessing LegacyRandomSource from multiple threads`，
   崩溃点是 `VaultBlockEntity$Client.emitIdleParticles`（试炼密室金库方块 tick 时的粒子随机数）。
3. 崩溃时 `Ribbon-LOD-Worker-10` 线程是**空闲**（LinkedBlockingQueue.take 阻塞），与崩溃无关。

**崩溃根因（与 LOD 无关，是环境模组冲突）**：
- ScalableLux（Starlight 光照优化 fork）开启 **6 个光照线程**（scalablelux-0~5），

  产生跨线程竞争，触发 cupboard 的 `ThreadingDetectorMixin` 崩溃。
- 这是 scalablelux + cupboard + vault 方块实体的已知兼容性问题，玩家靠近试炼密室时偶发。

**核心洞察（来自用户提供的 voxy 源码，决定性）**：
反编译/阅读 voxy（MCRcortex/voxy，1.4k star 的 Fabric LOD 模组）源码后，确认了正确做法：
1. voxy 有**两条渲染管线**：`IrisVoxyRenderPipeline`（光影）和 `NormalRenderPipeline`（无光影）。
2. Iris 路径的核心是 `IrisShaderPatch`——由**光影作者在 shaderpack 里声明的 JSON 补丁**，
   显式暴露哪些 G-Buffer 目标（opaqueDrawTargets/translucentDrawTargets）、uniforms、SSBO、
   image set 给 LOD。voxy mixin 到 `IrisRenderingPipeline.<init>`，把 LOD 网格**渲染进 Iris 的
   G-Buffer 目标**（真正参与 deferred 光照/雾/合成），而不是往主 framebuffer 贴一层。
3. voxy 用 Sodium 的 `ChunkRenderMatrices`（`cameraState.projectionMatrix` +
   `cameraState.viewRotationMatrix`）+ `CameraRenderState`，不是 NeoForge 事件矩阵。
4. voxy 从 Sodium `RenderSectionManager` 拿 `sourceDepthTexture`（原版已渲染地形的深度纹理）
   和 `sourceColourTexture`，在不透明 pass 后用 `closerEqualDepthCompare()` 做深度测试。
5. voxy 是 Fabric，通过 mixin 到 Sodium `RenderSectionManager` hook 渲染时机，非通用渲染事件。

**结论（务实判断）**：
- 当前方案（自定义 shader + 在 RenderLevelStageEvent.AFTER_TRANSLUCENT_BLOCKS 画到主 framebuffer）
  在**无光影**时应该能正常显示（framebuffer 一致、draw 成功、矩阵正确）。
- 在 **Iris deferred 光影**下，正确显示需要像 voxy/DH 那样深度集成进 G-Buffer（需要光影作者
  在 shaderpack 里加 patch），当前方案即使画上了也只是"贴纸"（无光照/无正确雾/可能被 composite 覆盖）。
- 用户的光影 Derivative 在 DH 的适配列表里，说明完整方案应参考 DH 的 `DHCompat` 接口。

## 第十一轮：LOD「一直看不到」真根因 = 环带是「空心」的（每圈只生成四条边）

**用户反馈**：仍看不到，怀疑"其他功能在捣乱（有个很强硬的剔除功能）"。

**日志铁证（22:09）**：
1. `候选=18, 投影可见=18`，但心跳 `ready=409`（且持续 408~413）。
2. 18 个"幸存"区块零散分布、中心约 (0,0)，相机在 (-18,11)。
3. ready=409 → 候选=18 的巨大落差，唯一解释是 evictFarAway 在 snapshotReady 之前
   把相机半径外的 mesh 全淘汰了，只剩零散历史残留。

**排除「剔除功能捣乱」**（逐项查证）：
- EntityCullingManager / BlockEntityCullingManager / MixinEntityRenderer 只作用于
  `Entity`/`BlockEntity` 的 shouldRender，**完全碰不到 LOD 地形**（LOD 是自建 VBO +
  独立 shader，走独立 LODRenderEventHandler 路径）。
- `LODFrustumCuller` 类虽仍 import，但**已无任何调用点**（LODRenderEventHandler 早已改用
  meshVisibleInView 矩阵投影剔除）。`frustumCulling` 配置开关是死配置。
- Embeddium 的 OcclusionCuller/FrustumMixin 只影响原版区块渲染，LOD 不经过那条管线。

**真根因（代码级，非"别的功能"）**：`MixinLODLifecycle` 请求环带的循环**每圈只 add 四条边**：
```java
for (ring=innerRadius..outerRadius) for (i=-ring..ring) {
    add(顶边); add(底边); add(左边); add(右边);  // 只有边界线！
}
```
环带内部（ring 与 ring 之间）**完全没请求**，结果 LOD 是一圈圈同心方框的"边"，不是连成片的
实心环带。高空俯视时视野里只有零散边，大片虚空。这就是"一直看不到"的元凶——不是被剔除，
而是**环带根本没生成实心覆盖**。

**修复**：`MixinLODLifecycle` 环带改成实心填充：
```java
for (dx=-outerRadius..outerRadius) for (dz=-outerRadius..outerRadius)
    if (dx²+dz² ∈ [innerRadius², outerRadius²]) wanted.add(center+dx, center+dz);
```
圆环带实心覆盖，请求区块数约 π·outer² - π·inner²（renderDistance=6、radius=8 时约 500 区块）。

**编译**：./gradlew build BUILD SUCCESSFUL（10s）。

**待用户**：进游戏测试。这是真正的根因——之前"空心环带"导致 LOD 只是零散方框边，
高空俯视永远填不满。实心填充后应能看到连成片的 LOD 环带。
